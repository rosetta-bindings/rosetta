# E6 — Case study: one library, many consumers, one new class

**Question.** A case study can assert anything. This one asserts that a library
can grow a class and every consumer acquires it with no binding change — so the
assertion is checked here instead of described, and the check fails loudly if it
ever stops being true.

**Claim under test** (paper §11): growing the library moves the *metadata* and
nothing else. Specifically, the stage-2 binding of `rosetta::script` — the
artifact every host actually imports — must be byte-identical before and after.

## Running it

```sh
./run.sh          # both arms + the comparison, ~2 min
./run.sh clean
```

Needs `clang-p2996` and `bin/rosetta_gen`. Nothing else: no Python, Node, Qt or
emsdk, because like E1–E3 and E5 this stays inside the generation stage.

## Method

The subject is `examples/dynamic` (the library `scene.h`, plus its metadata
tables) and `examples/scriptable-model` (the binding of `rosetta::script`). The
library grows one class, `scene::Relaxer` — a mesh-relaxation solver.

The two arms differ by **one line of the manifest**:

| arm | manifest class list |
|---|---|
| `before` | `Vec3`, `Mesh`, `Shading` |
| `after` | `Vec3`, `Mesh`, `Shading`, **`Relaxer`** |

`scene.h` is byte-identical in both. That matters: it means the comparison
isolates *a binding surface growing* from *a source file being edited*, which a
naive before/after on the header would confound.

Each arm runs both stages — stage 1 emits the library's metadata tables, stage 2
emits the scriptable binding pointed at those tables — and every generated file
is hashed and compared.

### The prediction is asymmetric

Both halves are asserted, and the analysis fails on either:

1. **The metadata MUST differ**, and `Relaxer` must be present in the *after*
   tables and absent from *before*. Without this the comparison could pass
   vacuously by generating nothing twice — the failure mode any byte-identity
   test invites.
2. **The scriptable binding MUST NOT differ**, at all. It is a binding of the
   reflection API, not of the library, so a library that grew by a class must
   not move it by a byte.

One normalisation is applied and is worth stating: generated `CMakeLists.txt`
files embed the absolute path of their configuration directory, which contains
the arm name. Left alone every file would differ for a reason that has nothing
to do with the library. Paths are rewritten to a placeholder before hashing —
the same normalisation E2 documents, for the same reason.

## What is NOT checked here, and why

The harness proves the *generated* artifacts do not move. It does not prove the
hand-written consumers still work, because they are not regenerated at all —
diffing them would trivially return zero and prove nothing.

That half of the claim is evidenced by version control instead. Adding the
solver touched exactly three files, all of them the library's own:

```
M examples/dynamic/scene.h          the solver
M examples/dynamic/Mesh.ann.json    one annotation for a new accessor
M examples/dynamic/manifest.json    one line: the class list
+ examples/dynamic/Relaxer.ann.json the solver's annotations
```

and no consumer: not `examples/dynamic/qt/` (the Qt viewer, property panel and
console), not `interp.h` (the terminal interpreter), and none of the five
scriptable drivers (`drive.py`, `drive.js`, `drive.lua`, `drive_qt.py`,
`drive_web.html`). Yet all of them gained the solver — the generated registry
inspector lists its fields with their ranges and read-only flags, the console
runs it, and the Python driver's property sheet grows its rows.

## Threats to validity

- **One library, one added class.** The check establishes that this addition
  cost nothing downstream, not that every addition would. A class the dynamic
  model cannot marshal would still be recorded as skipped rather than break the
  binding, but that is E5's claim, not this one.
- **Generated artifacts only.** See above: the hand-written half rests on the
  version-control evidence, which is weaker than a mechanical check.
- **The solver is ours.** `scene.h` is a demonstration library written for this
  repository, not third-party code. E5 is where the third-party evidence lives;
  this experiment is about the pipeline's shape, and uses a library small enough
  for a reader to hold in their head.
